# Attention reports and operator-controlled positions

Automatic position closing is disabled. The application remembers the last verified exposure on each durable intent, with a UTC timestamp, and continues read-only reconciliation after restart. That record is historical evidence, never current flatness or execution authorization. Broker SL/TP and provider-side actions remain independent of the application.

Technical errors, protection discrepancies, legacy risk thresholds and scheduled exit reminders pause entries and generate local attention reports. They never cancel protection or close exposure. Only your authenticated, password-confirmed local emergency Flatten action can request closing. A pending entry can be cancelled automatically only while wholly unfilled with no current or previously verified exposure; partial remainders require operator review. The schedule's legacy `flatten` field is an exit reminder, not enforced closing. Legacy limits are not guaranteed daily-loss or floor protection.

## Optional Discord delivery

Open **Connection settings → Discord attention reports**. Supply a Discord incoming webhook URL, enable reports, and confirm with your administrator password. Leave the URL blank to retain it; disable reports to stop new deliveries, or remove the saved webhook. Notification settings are independent of connection/trading settings and can be changed while a position is open. Saving them never arms, pauses or submits trades.

The webhook is stored in `attention-discord.json` inside the private state directory with mode 0600, never rendered back into HTML or included in logs/status. Only HTTPS `discord.com` API webhook paths are accepted; proxies and redirects are disabled. The sender has no trading client or inbound command handler.

Execution attention/error reports include account ID, fixed diagnostic text and UTC time. No signal payload, order request, ProjectX credential, webhook credential or raw provider response is sent. Reports use Discord `allowed_mentions.parse: []` so content cannot ping users or roles. `wait=true` requests confirmation. Official references: [Execute Webhook](https://docs.discord.com/developers/resources/webhook#execute-webhook) and [rate limits](https://docs.discord.com/developers/topics/rate-limits), reviewed 2026-11-16.

Delivery runs in a separate bounded worker, with an eight-second HTTP timeout and a 64-report queue. Identical reports are suppressed for five minutes; tracking is bounded to 256 distinct messages. Queue/tracking overflow is counted in settings. Reports are best effort, not durable: offline delivery, suspension, process exit or queue overflow can lose them. Reports produced while disabled are discarded; saving settings invalidates queued reports from the previous configuration. An already in-flight request cannot be recalled.

The worker honors Discord rate/reset headers and `Retry-After`/`retry_after` on HTTP 429, with a conservative 60-second cooldown if no valid delay is available (bounded to 24 hours). It does not retry a report after errors or ambiguous delivery. HTTP 401/403/404 suspends delivery until settings are saved again. The local dashboard shows fixed delivery errors, last confirmed send and overflow counts without exposing response bodies or webhook URLs. Delivery failure never changes a trading position or triggers emergency management. Local monitoring is the authoritative report; Discord is optional convenience.

Only mocked HTTP transports and synthetic accounts were used in tests. No real Discord message or trading request was sent during development.

## Separate daily trading reports

Connection settings now has a second, independent **Daily trading reports** form with its own enable toggle, secret webhook, delivery status and administrator-password confirmation. Its settings live in private `trading-discord.json`; changing or removing this webhook never changes the system-attention webhook. Both default off. Existing system settings retain their original path and behavior.

As confirmed by the operator, reports become due at **16:15 America/Chicago** on weekdays, checked once per minute while the service runs. The reporting window is the previous calendar day at **17:00 Chicago through the report date at 16:00 Chicago**. DST is handled by Chicago timezone rules. This is an explicitly chosen reporting convention, not exchange-calendar authorization or a claim about official settlement/merged-holiday accounting. Holiday windows report the history available within those declared timestamps; they never authorize trading.

The scope includes every configured Trade Manager account, the selected connection/manual account, and any account with a bot intent dated in that window's trading date. Duplicate accounts are combined; different accounts receive separate messages so one target cannot hide another. Account-wide history includes manual trades as well as bot trades. Missing/inactive/unverified accounts receive an unavailable-data report rather than fabricated zero results.

Each account's report includes opening/closing leg counts, closed-contract quantity, gross winning/losing/break-even closing legs, gross realized P&L, fees, commissions and net gross P&L less all costs charged within the reporting window. Opening-leg costs count too. Closing legs are explicitly not round-trip trade counts. Unrealized P&L is excluded. Nil costs make costs/net unavailable; duplicate identities, invalid amounts, mismatched account/time scope or read failures produce an unavailable-data report. Empty valid history reports no trades/zero realized totals.

These calculations follow the official [ProjectX trade-search reference](https://gateway.docs.projectx.com/docs/api-reference/trade/trade-search/), reviewed 2026-11-16: null P&L denotes opening legs, closing legs carry gross P&L, costs are distributed across legs, and voided legs are excluded. Corrections can arrive later; a sent report is a snapshot, not final settlement or a protection guarantee.

A read-only client and the shared ProjectX request governor are used. No order/position mutation or fresh-risk-check cache is added. Preparation is bounded and independent of execution/Discord workers. A unique `(report date, account ID)` record in `daily_trading_reports` saves the sanitized summary and durably claims the delivery attempt before queueing. It does not prove successful Discord delivery. Claims survive restart, and failed/ambiguous/overflowed sends are not replayed automatically. On restart or first enabling, only the most recent completed weekday is considered; there is no older backlog. Reports require the app and network to be available and remain best effort. No real webhook message or trading request was sent during development.

System-attention messages now link to the authenticated local **System health** checklist, using the configured loopback dashboard address. This is a diagnostic link for the laptop, never a public admin route or a remote trading action. No automatic recovery notification is added. The checklist separates current state from retained locks and historical triggers, and does not probe Discord or create new broker traffic. [Checklist behavior and limits](admin-guide.md#system-health-checklist).

## Hourly automation profile status

System Discord settings now include **Also send hourly automation profile status**. It uses the existing system-attention webhook, independently of the daily trading webhook. Both the main system-report enable toggle and the hourly option must be enabled; the hourly option defaults off. Saving requires the existing administrator password and CSRF checks, preserves a blank webhook field, and never pauses or arms trading. Older clients omitting the hourly setting preserve its saved value.

The running service checks once per minute and prepares at most one snapshot for the current UTC clock hour. The first eligible check after enabling/startup can send the current hour immediately; subsequent hours send on the first check after the hour changes. UTC hour keys keep the repeated Chicago DST hour distinct. There is no missed-hour backlog, and the app/device must be running and online.

Every configured automation profile is included, in stable ID order. Reports distinguish Running, Waiting for readiness/session, Waiting for recovery, Paused, Paused while monitoring an execution, Monitor unavailable, Global pause and Review only. Each line includes configured target count, currently armed accounts (expired arming is not counted), accounts with active executions, recovery waits and retained current locks. Captured active executions remain visible even after configured targets change or restart leaves an account unreserved. Active executions from removed/unconfigured profiles get explicit retained-monitoring rows; unsafe historical identity text is replaced with a fixed label. Armed/Running is not a promise that an incoming signal passes fresh broker/risk checks, and managing an execution is not proof of verified SL/TP.

Preparation reads only stored policies, the existing fleet telemetry, local lock records and existing quote caches. It does not call a broker, warm market data, probe Discord, change ownership/arming or replay alerts. Free-form profile names, execution messages, gateway errors, signal payloads and credential-bearing settings are excluded. Only validated profile IDs, fixed state labels, counts, UTC capture time and the configured dashboard link are used. The optional remote link remains protected by Access and app authentication; it grants no execution authority.

Large snapshots are split at profile boundaries into numbered parts rather than truncating profiles. Preparation supports up to 32 parts and fails visibly beyond that bound rather than omitting rows. Each part stays below Discord's content limit, uses the distinct “hourly automation status” heading and disables mentions. The existing bounded nonblocking sender, timeout, rate-limit handling, settings-generation invalidation and no-retry behavior apply. Preparation/delivery failures only produce reporting diagnostics and never affect positions, SL/TP or trading permissions.

The complete sanitized snapshot is durably claimed once in `hourly_automation_reports` before queueing any part. A claim is not delivery confirmation. Restart, repeated scheduler checks or changing the webhook do not resend that hour. Failed, ambiguous or overflowed sends are not automatically replayed; numbered parts make incomplete delivery visible, and queue overflow appears in report settings. Tests use temporary databases and mocked transports only; no live Discord message is sent during development.

Discord payload constraints were checked against the official [webhook reference](https://github.com/discord/discord-api-docs/blob/main/developers/resources/webhook.mdx): content is limited to 2,000 characters, with explicit `allowed_mentions` and `wait=true` confirmation behavior.
