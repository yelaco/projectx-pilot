YOUR FIRST AUTOMATION

Quick start

Use the computer that will run ProjectX Pilot and originate its trading API requests. Start with a Practice account while you verify your setup.

  1. Connect ProjectX

    In Settings → ProjectX connection, enter your exact TopstepX platform login and API key. Your login may be an email. Save, then check Accounts for the correct account ID and trading permission.

  2. Create a Trade Manager

    In Trade managers, select one or more explicit accounts and set the maximum planned risk per trade. Each target account gets its own risk budget.

  3. Create an automation profile

    In Automations, set its strategy identifier, instruments, and Trade Manager. Under Automatic execution → Signal routing, choose automatic handling, the actual contract expiry, and Market or Limit entry.

  4. Save trading setup

    Set estimated round-trip costs, slippage reserve, maximum contracts, and price-deviation tolerance. Confirm the selected accounts, Auto OCO, and reviewed session calendar. Save with your administrator password. Saving does not arm an order.

  5. Connect TradingView delivery

    Enable receiving in Settings → Webhook & tunnel. Configure HTTPS delivery to the receiver. Set the profile's price mappings, then copy its complete webhook URL and generated BUY/SELL messages into TradingView. Verify all numeric placeholders resolve.

  6. Start and verify every target

    Click Start automation on the profile. Open Execution runners and check each target is armed and accepting eligible signals. New valid alerts can then execute automatically, without per-alert approval.

Start is not the same as ready. “Account runners active; inspect per-account readiness” confirms the run was requested. Some targets may still be waiting or blocked. Alerts received before a target is armed are blocked permanently; they do not fire later.

Connection & accounts

The account selected in Connection settings is your monitoring account. Automatic execution targets come from the profile's Trade Manager, using pinned numeric account IDs. Incoming alerts cannot choose arbitrary accounts.

Platform login
Use the exact login that authenticates with TopstepX, including an email if that is your platform username. Use an API key, not your account password.
Refresh interval
Controls periodic account/contract discovery. It does not schedule webhook dispatch. Fresh account, exposure, session, quote, and risk checks still run before an entry.
Account permission
Local execution permission and ProjectX canTrade are separate. A local permission cannot override a provider restriction. Automatic targets must also have API-verified simulated status.

If credentials are managed by service environment variables, the dashboard shows that and does not override them. Manage administrator logins separately in Settings → Admin access.

Trade managers & position sizing

A Trade Manager supplies the account routing, risk policy, and recurring start/last-entry/flatten schedule in America/Chicago. New and re-saved simplified managers enforce planned risk per trade; they do not calculate MLL or enforce cumulative daily-loss, trade-count, or portfolio limits. Existing legacy policies keep their saved limits until explicitly changed.

Estimated risk per contract

stop ticks × tick value + slippage reserve + round-trip costs

Automatic quantity

min(maximum contracts, floor(available risk / risk per contract))

Tick size and tick value come from authoritative contract metadata. Quantities round down to whole contracts; less than one contract is rejected. Fees, commissions, and slippage estimates are part of the budget. Actual loss can exceed planned risk during gaps or adverse execution.

Risk multiplies across targets. A $150 per-trade manager targeting four accounts can plan up to $600 across that signal. Targets execute independently: one can be accepted while another is blocked or uncertain.

Account ownership

One running profile owns an account. Profiles on distinct accounts can run concurrently; two profiles cannot share a running account, even for different instruments. Pause the old profile and resolve its working or uncertain execution before changing owner. A manager supports up to 20 targets; multi-account routing requires per-trade-only risk.

Automation profiles

Each profile binds a strategy identifier, its own instrument scope, Trade Manager, contract expiry, order type, webhook credentials, mappings, and saved trading setup. There is no separate global instrument allowlist in Connection settings. Keep separate strategies in separate profiles and review pinned contracts when they roll.

Review only

Alerts go to the inbox for local review. Reviewing or importing an alert does not submit an order.

Automatic execution

After explicit Start and account arming, eligible new alerts run through risk checks and the execution engine without an approval click for each alert.

Saving account/risk/routing or Trade Manager schedule changes pauses affected profiles and may require trading-setup confirmation again. Existing positions retain the policy captured when their trade was submitted. Restart always leaves profiles paused.

Price mappings

Choose shared BUY/SELL placeholders or separate entry, stop-loss, and take-profit mappings per direction. Use verified indicator outputs that become numeric values. Unresolved placeholders and wrong-side stops/targets are rejected. Message templates containing delivery tokens are private; do not put them in logs, screenshots, or public issues.

Webhook & HTTPS delivery

The dashboard uses local port 8080. The notification receiver uses 127.0.0.1:8090. Configure public delivery to the receiver only; never tunnel the dashboard, guide, or trading controls.

Quick Tunnel
The dashboard preset starts a test tunnel. Its HTTPS hostname can change when recreated; update TradingView if it changes.
Named tunnel
Use a domain/hostname you control for a stable URL. Configure Cloudflare's public hostname to forward to HTTP 127.0.0.1:8090, then save the matching public HTTPS base URL in webhook settings.
Profile URL & token
Copy the full generated URL from the profile rather than constructing it manually. The generated message includes its private delivery token. Token rotation invalidates previously pasted messages.

For named-tunnel installation, after creating the domain/tunnel/route in Cloudflare:

./scripts/install-user-service.sh --named-tunnel alerts.example.com

The installer prompts for the tunnel token privately. That token is different from the webhook delivery token and ProjectX API key. Configuring a tunnel does not establish provider permission for the remote-trigger workflow.

How an alert reaches a runner

The receiver validates and saves the alert in SQLite, then sends a one-byte Unix socket notification to wake local dispatch. SQLite holds the alert; the socket carries no signal payload or execution authority. A missed notification has a 30-second scan fallback, subject to freshness and arming checks.

HTTP 202 means the alert was stored, not that an order was accepted. Identical repeated IDs are deduplicated; conflicting content under an existing ID is rejected. Generated IDs allow one distinct entry per direction/bar. Old, busy, paused, pre-arming, and interrupted claims are not replayed later.

Entry orders & protection

Market entry

Requests execution at the available market. A signal's reference entry is not a guaranteed fill price. Fresh quotes and any configured deviation limit still apply.

Limit entry

Works at the signal entry price. The unfilled remainder expires 30 minutes after the original signal timestamp; Pause or session management can cancel it sooner.

Auto OCO must be enabled in the platform and confirmed in trading setup. Entry requests include stop/target tick offsets; protective children attach to resulting fills. An unfilled limit entry is not an open position. After a partial fill, the remaining entry and protection for filled exposure are monitored separately.

Brackets are relative to actual fills, so final absolute SL/TP prices can differ from the signal reference. The engine verifies linked protective orders and matching exposure. Missing or inconsistent protection triggers the fail-safe, blocks entries on that account, and requests emergency management. Inspect the account in TopstepX if protection or flatness cannot be verified.

Only entry alerts are supported. Remote TP/SL exit signals and replacement-entry workflows are unsupported. The service must be running and connected to perform local expiry/cutoff management; broker-side brackets remain essential during laptop outages.

Practice API tests

Practice execution tests real API order submission on a confirmed PRAC account, without an automation profile. Market/Limit buttons calculate a preview; a separate password-confirmed approval submits. Exact contract quantities must fit risk and are never silently resized. Practice orders still reach ProjectX; this is not paper simulation.

Operation days, sessions & news

Use Operation days to plan a Saturday–Friday week. General blocked dates apply to all managers; manager-specific dates add restrictions and cannot override a general block. These are saved dates, not recurring weekday rules—review each new week.

The US FOMC policy-event filter uses the Forex Factory weekly feed. It refreshes automatically and retains cached events. Missing/stale coverage alone does not block a date; known cached matching event blocks remain. It is not a filter for every important US release. Manual operation-day restrictions still apply when news data is missing.

Sessions use America/Chicago, independently of your desktop timezone, including daylight-saving changes. The default Trade Manager accepts entries from 17:00 the previous evening until 15:00 Chicago and flattens by 15:05. Change these times in Trade managers to fit the selected products. One window applies per weekday; last entry must precede flatten by at least two minutes, and flatten must be by 15:08. Choose narrower windows for earlier closes and daily pauses. Reviewed early-close days cap the selected times with additional margins. A running profile can wait through closures and reconcile into the next verified session without another click.

Calendar coverage is bounded. The manager chooses the operating window; there is no MNQ/MGC symbol-name gate. Confirm the window fits the selected contracts’ official hours. Reviewed 2026 holiday cutoffs can only shorten it; unknown holiday years and unsupported merged sessions cannot authorize automatic trading. Revision: {{.CalendarRevision}}.

Latency & connections

Timing separates local webhook arrival → worker, checks → submission, submission → acknowledgement, and total acceptance. It excludes delivery before the receiver and does not measure fill latency. Network response and shared API-budget waits can dominate local dispatch time.

Runners share authentication, HTTP connections, contract metadata and quote subscriptions, and user events. Their account risk and orders remain separate. User events wake authoritative REST reconciliation; reconnect restores subscriptions and triggers fresh checks. Automatic active polling remains an adaptive backstop, not a replacement for server-side protection.

Pause & emergency controls

Pause profile / account
Stops new entries and retains position monitoring. The engine requests cancellation of any working entry remainder. An already durably reserved submission may finish its bounded one-time attempt.
Pause all entries
Closes a persistent global entry gate for automatic and manual arming. Resume clears only that gate; explicitly Start the desired profiles again.
Flatten account / profile / all
Password-confirmed closing/cancellation for the relevant managed executions. A request is not proof of flatness; verify every account's outcome. Flatten all also includes active manual recovery.

Pausing the application does not mean all positions are closed. Do not assume stopping a terminal, service, tunnel, or computer closes broker exposure. Keep TopstepX available for independent management.

Updates, laptop operation & recovery

Pause automation, independently verify every account is flat with no working orders, and resolve any uncertain intent before upgrading. From an existing checkout that already uses the current Git history:

git pull --ff-only
./scripts/install-user-service.sh

The installer preserves saved credentials, profiles, databases, and webhook settings. It refuses an unresolved execution. Ordinary updates do not require reconfiguring the named tunnel. Services retain their existing projectx-bot, projectx-webhook, and projectx-tunnel names.

systemctl --user status projectx-bot projectx-webhook
journalctl --user -u projectx-bot -n 50 --no-pager
journalctl --user -u projectx-bot -f

After restart, inspect recovery and Start the desired profiles again. Existing positions/orders are reconciled; placement is never replayed. Global pause, session locks, durable claims, and emergency latches survive restart. Never delete or replace a database to clear a gate.

Keep the laptop powered, connected, ventilated, and awake during intended operation. Screen lock does not itself stop a user service, but suspend, lid-close policy, battery depletion, and shutdown can. Verify your own power settings; ProjectX Pilot does not change them. Back up private state consistently only after shutdown with accounts independently verified flat.

Troubleshooting

The profile says active, but the account is not armed

Open Execution runners and read that account's message. Check global Pause, account ownership, current market window, saved setup, ProjectX permission, existing exposure, and local lockouts. Start is a running choice, not proof every target is ready.

The webhook returned 422

Inspect the validation message and generated template. Check required numeric prices, timestamp freshness, strategy, symbol, stop/target direction, and unresolved TradingView placeholders. Never put credentials or full token-bearing payloads in shared logs.

The webhook arrived, but no order appeared

Find the delivery in Inbox, then inspect its per-account outcome and runner. HTTP 202 only confirms persistence. An alert received while disarmed/busy or before arming is consumed as blocked, not delayed until later.

The webhook URL changed

Quick Tunnel hostnames can change when recreated. Use a named tunnel with a domain you control for a stable address. Save its public HTTPS base URL, then copy the profile's complete URL into TradingView.

Signal price exceeds the market-deviation limit

The entry/reference price is outside the configured tolerance. Check the contract expiry, alert freshness, and intended limit price. The profile's Trading setup can explicitly disable this guard; freshness, tick alignment, risk, quotes, and protection checks remain active.

Submission requires reconciliation

Keep monitoring and inspect the account in TopstepX. Review the order ID, working orders, positions, and submission diagnostic. An ambiguous request must never be blindly retried with the same or a new signal ID.

The bot says locally locked, but TopstepX can trade

The bot's session/fault lock is independent of provider permission. Read the original management trigger and verify protection/flatness. Restarting does not clear it. The legacy OCO review only handles its exact historical false-alarm case with verified evidence; it is not a general unlock.

Another profile owns the account

One profile owns each running account. Pause its owner and resolve the working/uncertain execution before switching. Use distinct target accounts for concurrent profiles; do not create another state directory to bypass ownership.

Supported scope & provider policy

Automatic targets must be API-verified simulated Practice, Trading Combine, or Express Funded accounts with trading permission. Live Funded is unsupported. Manual tests remain PRAC-only. Automatic MLL discovery, paper simulation, local strategy generation, arbitrary order modification/trailing, and calendars beyond reviewed coverage are not implemented.

ProjectX Pilot is an independent community project, unaffiliated with ProjectX or Topstep. Local order execution and tunnel setup do not establish permission for cloud-originated triggers. Confirm your intended workflow against the official Topstep API policy. All trading API requests originate directly from the operator's computer.

See the repository documentation for architecture, API evidence, deployment, and detailed recovery procedures.
